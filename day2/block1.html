Lab 1: Tests you can trust

Goal: see why tests written from a spec catch bugs, and tests written from the code do not. About 35 minutes.

Folder: day2\block1. It has rates.py (price calculator) and rates-spec.md (what it SHOULD do). rates.py has 2 hidden bugs.

Part A: tests from the code (the lazy way)

📝 EDITOR
Open block1\rates.py. Skim it. Do not read the spec yet.
💬 COPILOT CHAT
Ask Copilot to write tests from the code only:
Look at #file:rates.py and write pytest tests for quote(). Save them in block1/test_from_code.py. Aim for good coverage.
🖥️ TERMINAL
Run them:
cd C:\EYLAB\ey-aidevops-labs\day2\block1
python -m pytest -q
Predict first: Will all tests pass? Do you think the code is correct because they pass?

Part B: tests from the spec

💬 COPILOT CHAT
Now give Copilot the spec, not the code:
Read #file:rates-spec.md. Write pytest tests for quote() in block1/test_from_spec.py. Use every worked example in the table and every edge case. Do NOT read rates.py. Import it with: from rates import quote
🖥️ TERMINAL
Run only these:
python -m pytest test_from_spec.py -q
Predict first: Some tests should now FAIL. Each failure points at a bug.
💬 COPILOT CHAT
Ask Copilot to explain, then YOU decide:
Here is the failing output. For each failure, tell me which line in rates.py is wrong and why. Do not change the spec.
📝 EDITOR
Fix the 2 bugs in rates.py yourself, using Copilot's explanation as a hint. Run pytest again until everything passes.

Check yourself

⭐ Takeaway

Tests written from the code just repeat the code, bugs included. Give the AI the requirement, not the implementation. A green test run only means something if the tests came from somewhere independent.

Reusable prompt:

Read the requirement in #file:SPEC. Write pytest tests for FUNCTION using every example and edge case in it. Do not read the implementation. If the spec is unclear, list your questions first instead of guessing.
